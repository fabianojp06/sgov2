# Trilha 2027 · P2 VPS (frente B) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task (sessão única: são operações no servidor de produção, em sequência, com o PO acompanhando). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deixar a VPS pronta para receber o dev das duas frentes sem risco para a produção (D12) e endurecida para o go-live (US-016).

**Architecture:** Configuração do host Ubuntu da VPS Hostinger srv2039095, que já roda Docker (swarm do Easypanel) e Traefik em 80/443. Nada aqui altera contêineres existentes. Os scripts e a documentação são versionados em `ops/vps/` e `docs/operacao/` (pastas da frente B).

**Tech Stack:** Ubuntu (systemd, sysctl, apt), earlyoom, ufw + cadeia `DOCKER-USER` do iptables, fail2ban, unattended-upgrades, firewall do hPanel da Hostinger, stress-ng (só no teste).

**Spec:** `docs/superpowers/specs/2026-10-24-sgo-v2-especificacao-oficial-design.md` (v1.1) — §4.3 (segurança da VPS e D12), §11.5 itens 1 e 6, §12.4. **Plano-mestre:** `docs/superpowers/plans/2026-10-24-trilha-2027-plano-mestre.md`.

## Global Constraints

- **Antes de qualquer passo, o PO tira um snapshot da VPS no hPanel** e confirma no chat. Sem snapshot, nada começa.
- Cada comando que **altera** o host é anunciado antes ("isto escreve/altera X; para desfazer, Y") e só roda com o "ok" do PO (spec §11.5 item 5, por analogia).
- Nenhum passo toca contêineres, volumes ou redes do Easypanel (`easypanel`, `easypanel-traefik`, futuros `sgo-prod`/`sgo-hml`).
- Portas abertas para a internet ao final: só **22, 80 e 443**. O painel do Easypanel (3000) só por túnel SSH até existir o subdomínio HTTPS (GAP-INF-001).
- Gatilho de revisão de D12: mais de 3 alertas de memória por semana, qualquer OOM que atinja a produção ou qualquer incidente de acesso → o dev sai da VPS.
- Período de fundação (spec §12.3): os passos no host podem rodar já; o PR com `ops/vps/` e `docs/operacao/` só é aberto depois do merge da US-001.
- Branch `us-122-mitigacoes-d12` e `us-016-hardening`, labels `frente:B`, commits com `Frente: B`.

## Review Focus

1. **Trancar o PO fora da VPS** ao desligar a senha do SSH: esperado que o login por chave seja testado numa **segunda** sessão antes do `reload`, e que a sessão atual fique aberta até a confirmação — passo obrigatório na Tarefa 2.
2. **O Docker ignora o ufw**: portas publicadas por contêineres (como a 3000 do Easypanel) continuam abertas mesmo com `ufw deny`. Esperado: bloqueio na cadeia `DOCKER-USER` e no firewall do hPanel, conferido **de fora** da VPS — Tarefa 2.
3. **O earlyoom matar a produção**: o app de produção também é um processo `node`. Esperado: produção com `oom_score_adj` negativo e o earlyoom evitando `postgres`, `dockerd`, `containerd`, `traefik`, `sshd` — teste de pico na Tarefa 1.
4. **Swap mal configurado deixar tudo lento**: com `swappiness` alto, o Postgres de produção vai para o disco. Esperado: `vm.swappiness=10` persistido após reboot — verificação na Tarefa 1.
5. **Alerta que ninguém recebe**: sem canal definido, o alerta vira só log. Esperado: com `ALERTA_WEBHOOK_URL` vazio, o script grava no journal **e** no contador semanal, e o PO é avisado de que o canal está pendente — teste do script na Tarefa 1.

### Task 1: Mitigações da convivência do dev com a produção (US-122, #145)

**Files:**
- Create: `ops/vps/90-sgo.sysctl.conf`, `ops/vps/earlyoom.default`, `ops/vps/ajustar-oom.sh`, `ops/vps/alerta-memoria.sh`, `ops/vps/sgo-oom.service`, `ops/vps/sgo-oom.timer`, `ops/vps/sgo-alerta-memoria.service`, `ops/vps/sgo-alerta-memoria.timer`, `ops/vps/instalar.sh`
- Create: `docs/operacao/vps.md`
- Test: `ops/vps/testes/ajustar-oom.bats`, `ops/vps/testes/alerta-memoria.bats` (bats-core), verificações no host

**Interfaces:**
- Produces: `ajustar-oom.sh [--simular]` — para cada contêiner em execução, aplica `oom_score_adj` aos PIDs dele: nome iniciando em `sgo-prod` → `-500`; `sgo-hml` → `-200`; `sgo-a` ou `sgo-b` → `500`; os demais não mudam. Com `--simular`, só lista `contêiner pid valor`. `alerta-memoria.sh` — lê `MemAvailable` de `/proc/meminfo`; abaixo de `LIMITE_MB` (padrão 1024), grava no journal (`logger -t sgo-alerta`), acrescenta a linha `$(date +%G-W%V) $(date -Is) MemAvailable=<MB>` em `/var/lib/sgo/alertas-memoria.log` e, se `ALERTA_WEBHOOK_URL` estiver definido, faz um POST com o texto; sai com 0 sempre.

- [ ] **Step 1: Snapshot e linha de base** — o PO confirma o snapshot no hPanel. Registrar `free -h`, `swapon --show`, `docker ps --format '{{.Names}}'`, `cat /proc/sys/vm/swappiness` em `docs/operacao/vps.md` (seção "Antes").

- [ ] **Step 2: Escrever os testes bats (falham)** com `/proc/meminfo` e `docker` simulados por variáveis (`MEMINFO=arquivo`, `DOCKER=script-falso`):
  - `alerta-memoria.sh` com `MemAvailable: 900000 kB` → código 0, uma linha nova no log de alertas e uma chamada ao `logger`; com `2000000 kB` → nenhuma linha nova; com webhook vazio → não tenta POST;
  - `ajustar-oom.sh --simular` com contêineres falsos `sgo-prod_db.1`, `sgo-hml_app.1`, `sgo-a-db-1`, `easypanel.1` → imprime `-500`, `-200` e `500` para os três primeiros e nada para `easypanel.1`.

- [ ] **Step 3: Rodar e ver falhar** — `bats ops/vps/testes` → FAIL.

- [ ] **Step 4: Implementar os scripts** (bash com `set -euo pipefail`, aprovado no `shellcheck`). `ajustar-oom.sh` obtém os PIDs com `docker top <id> -eo pid` e escreve em `/proc/<pid>/oom_score_adj`.

- [ ] **Step 5: Rodar e ver passar** — `bats ops/vps/testes && shellcheck ops/vps/*.sh` → PASS.

- [ ] **Step 6: Swap** (anunciar: cria `/swapfile` de 8 GB e altera `/etc/fstab`; desfazer: `swapoff /swapfile`, remover a linha e o arquivo) — `fallocate -l 8G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile`, linha `/swapfile none swap sw 0 0` no `/etc/fstab`. Verificar: `swapon --show` mostra 8G.

- [ ] **Step 7: sysctl** (anunciar; desfazer: remover o arquivo e `sysctl --system`) — copiar `90-sgo.sysctl.conf` (`vm.swappiness = 10`, `vm.vfs_cache_pressure = 50`) para `/etc/sysctl.d/` e rodar `sysctl --system`. Verificar: `cat /proc/sys/vm/swappiness` = 10.

- [ ] **Step 8: earlyoom** (anunciar; desfazer: `apt remove earlyoom`) — `apt install -y earlyoom`; `/etc/default/earlyoom` com `EARLYOOM_ARGS="-m 5 -s 10 -r 3600 --prefer '(^|/)(node|next-server|vitest|tsx|esbuild|stress-ng)$' --avoid '(^|/)(postgres|dockerd|containerd|containerd-shim.*|traefik|sshd|systemd|earlyoom)$'"`; `systemctl enable --now earlyoom`. Verificar: `systemctl is-active earlyoom` = active.

- [ ] **Step 9: Timers** (anunciar; desfazer: `systemctl disable --now sgo-oom.timer sgo-alerta-memoria.timer`) — `ops/vps/instalar.sh` copia os scripts para `/usr/local/sbin/`, as units para `/etc/systemd/system/`, cria `/var/lib/sgo/` e `/etc/sgo/alerta.env` (`ALERTA_WEBHOOK_URL=` vazio e `LIMITE_MB=1024`) e ativa os dois timers (a cada 1 minuto). Verificar: `systemctl list-timers | grep sgo` mostra os dois.

- [ ] **Step 10: Teste de pico** (anunciar: força falta de memória por até 60 s; nesta data ainda não há `sgo-prod` na VPS) — em outro terminal, `watch -n1 free -m`; rodar `apt install -y stress-ng && stress-ng --vm 2 --vm-bytes 95% --timeout 60s`. Esperado: o earlyoom mata o `stress-ng` (`journalctl -u earlyoom` mostra "sending SIGTERM to process ... stress-ng") e `docker ps` continua mostrando `easypanel` e `easypanel-traefik` em execução, com `Up` maior que o tempo do teste. Depois, `apt remove -y stress-ng`.

- [ ] **Step 11: Teste do alerta** — `LIMITE_MB=999999 /usr/local/sbin/alerta-memoria.sh` → `journalctl -t sgo-alerta -n1` mostra o alerta, e há uma linha nova em `/var/lib/sgo/alertas-memoria.log`. Avisar o PO de que o **canal do alerta** (ntfy, Telegram ou e-mail) é decisão pendente e só falta preencher `ALERTA_WEBHOOK_URL`.

- [ ] **Step 12: Verificar os hooks das sessões** (depende da P1 Tarefa 2 na `main`) — numa sessão da frente B, pedir `docker exec -it easypanel sh` → bloqueado com motivo citando D12. Se a P1 Tarefa 2 ainda não estiver na `main`, deixar este passo pendente e anotar na issue.

- [ ] **Step 13: Documentar e abrir o PR** — `docs/operacao/vps.md` com o que foi instalado, onde, como desfazer e como ler o contador semanal (`grep -c "^$(date +%G-W%V) " /var/lib/sgo/alertas-memoria.log`; acima de 3 na semana, aciona o gatilho de D12). PR "[US-122] Mitigações da convivência do dev com a produção", `Closes #145` (só depois do Step 12), label `frente:B`.

### Task 2: Endurecimento da VPS (US-016, #38)

**Files:**
- Create: `ops/vps/sshd-90-sgo.conf`, `ops/vps/docker-user.sh`, `ops/vps/sgo-docker-user.service`, `ops/vps/jail-sgo.local`
- Modify: `ops/vps/instalar.sh`, `docs/operacao/vps.md`
- Test: verificações no host e de fora dele

**Interfaces:**
- Produces: `docker-user.sh` — idempotente; garante na cadeia `DOCKER-USER` a regra `-i <interface pública> -p tcp -m conntrack --ctorigdstport 3000 --ctdir ORIGINAL -j DROP` (sem duplicar), com a interface descoberta por `ip route get 1.1.1.1`. Roda no boot pela unit `sgo-docker-user.service` (`After=docker.service`).

- [ ] **Step 1: Chave SSH antes de tudo** — `test -s /root/.ssh/authorized_keys` e o PO confirma que entra **por chave** de um terminal novo (`ssh -o PreferredAuthentications=publickey root@<ip>`). Se não entrar, **parar** e configurar a chave primeiro.

- [ ] **Step 2: SSH só por chave** (anunciar; desfazer: remover o arquivo e `systemctl reload ssh` pelo console do hPanel) — copiar `sshd-90-sgo.conf` (`PasswordAuthentication no`, `KbdInteractiveAuthentication no`, `PermitRootLogin prohibit-password`) para `/etc/ssh/sshd_config.d/`; `sshd -t` (sem saída) e `systemctl reload ssh`. **Mantendo a sessão atual aberta**, o PO testa: `ssh -o PreferredAuthentications=password root@<ip>` → recusado; por chave → entra.

- [ ] **Step 3: Firewall do hPanel** (ação do PO no painel) — regras de entrada só para TCP 22, 80 e 443. Registrar em `docs/operacao/vps.md`.

- [ ] **Step 4: ufw** (anunciar; desfazer: `ufw disable`) — `ufw default deny incoming && ufw default allow outgoing && ufw allow 22/tcp && ufw allow 80/tcp && ufw allow 443/tcp && ufw --force enable`. Verificar: `ufw status verbose`.

- [ ] **Step 5: Fechar a 3000 também no Docker** (anunciar; desfazer: `iptables -D DOCKER-USER ...` e `systemctl disable sgo-docker-user`) — instalar e ativar `docker-user.sh` + unit. Verificar: `iptables -S DOCKER-USER` contém a regra uma única vez, mesmo rodando o script duas vezes.

- [ ] **Step 6: Conferir de fora** — o PO, do próprio computador: `nc -zv <ip> 3000` → recusado ou *timeout*; `nc -zv <ip> 443` → aberto. Acesso ao painel pelo túnel: `ssh -L 3000:127.0.0.1:3000 root@<ip>` e abrir `http://localhost:3000` → painel abre.

- [ ] **Step 7: fail2ban** (anunciar; desfazer: `apt remove fail2ban`) — `apt install -y fail2ban`; `jail-sgo.local` com `[sshd] enabled = true`, `maxretry = 5`, `bantime = 1h`, `findtime = 10m`; `systemctl enable --now fail2ban`. Verificar: `fail2ban-client status sshd` mostra a jail ativa.

- [ ] **Step 8: Atualizações automáticas de segurança** (anunciar) — `apt install -y unattended-upgrades` e `dpkg-reconfigure -f noninteractive unattended-upgrades`, sem reboot automático (`Unattended-Upgrade::Automatic-Reboot "false"`). Verificar: `unattended-upgrade --dry-run --debug 2>&1 | tail -3` sem erro.

- [ ] **Step 9: Reboot de prova** (anunciar; o Easypanel fica fora do ar por ~1–2 min) — `reboot`. Depois: `swapon --show` (8G), `cat /proc/sys/vm/swappiness` (10), `systemctl is-active earlyoom fail2ban sgo-docker-user` (active), `iptables -S DOCKER-USER` (regra presente), `docker ps` (Easypanel em execução), e `nc -zv <ip> 3000` de fora (fechado).

- [ ] **Step 10: Documentar e abrir o PR** — `docs/operacao/vps.md` com as portas, o túnel do painel, como desbanir um IP (`fail2ban-client set sshd unbanip <ip>`) e a pendência do subdomínio HTTPS do Easypanel (GAP-INF-001). PR "[US-016] Endurecimento da VPS", `Closes #38`, label `frente:B`.
